# 序文: なぜ今、再びShape Upなのか

2019年に世に出たShape Upは、一文に縮めれば「6週間という時間予算の中で、何を作るのかを先に整える」という本でした。Basecampは、この仕事にどれだけ時間がかかるかという見積もり(estimate)を出す代わりに、この問題にどれだけ時間を使う意思があるのかを先に決める[アペタイト](https://basecamp.com/shapeup/1.2-chapter-03)(appetite)を立てました。そして、その予算に収まるように解決策の輪郭をあらかじめ描く作業を[シェイピング](https://basecamp.com/shapeup/1.1-chapter-02)(shaping)と呼び、その成果物である[ピッチ](https://basecamp.com/shapeup/1.5-chapter-06)(pitch)を[ベッティングテーブル](https://basecamp.com/shapeup/2.2-chapter-08)(betting table)に載せて次のサイクル(cycle)を賭けたのです。時間を固定して[スコープ](https://basecamp.com/shapeup/3.3-chapter-12)(scope)を調整するという原則が、これらすべての仕掛けを貫いています。原作の全体像は[第1章: イントロダクション](https://basecamp.com/shapeup/0.3-chapter-01)にまとめられています。

本ガイド『Vibe Up』は、あの本がバイブコーディング(vibe coding)以後も有効なのか、有効だとすれば何が変わるのかを扱います。結論から言えば、原作の原理はその大半が生き残りますが、その原理が結びついていた数字や仕掛けは、かなりの部分で意味が変わります。本ガイドは、その境界線を引く仕事をします。

## 実装が安くなればシェイピングは不要になるのか

まず思い浮かぶ直感はこういうものです。計画が必要だったのは、作ることが高くついたからだ。間違って作れば数週間が吹き飛ぶから、何を作るかをあらかじめ整えていたのだ。ところが実装コストが0に収束するのなら、整えている時間でとりあえず作ってみたほうが速いのではないか。だとすればシェイピングも、アペタイトも、6週間という固定された期間も、一緒に消えるべきではないのか。

本ガイドの答えは逆です。**ボトルネックは消えず、移動します。** 作るコストが下がった分だけ、作られたものを確かめて責任を負うコストが上がり、何を作るかを選ぶ人間の注意力が相対的にいっそう希少になります。ボトルネックが移ったのなら、プロセスも移った先に立て直さなければなりません。原理を破棄するときではなく、原理が狙う的を合わせ直すときだ、というのが本ガイドの立場です。

興味深いことに、この読み替えを先に予告したのは原作の側でした。Basecamp共同創業者のDavid Heinemeier Hanssonは2026年4月のインタビューで「Shape Upが記述した2か月サイクルの終わり」に自ら言及し、AIによって開発が速くなった今、あのタイムラインは遅く感じられる、だから方法論を書き直すべきだと語っています([Pragmatic Engineerインタビュー](https://newsletter.pragmaticengineer.com/p/dhhs-new-way-of-writing-code))。ただし彼が同時に述べたのは、品質と職人気質の基準はそのままだという点、そしてエージェントで出し続けるドーパミンループがかえってバーンアウトのリスクを高めるという警告でした。変えるべきものと守るべきものが分かれている、ということです。本ガイドはその分離線に沿って進みます。

## 本ガイドの構成

全体は3部、七つの章です。

- **第1部: 何が変わったか** — 実装コストが実際にどこまで崩れ、何はそのままなのかを見たうえで、新たに希少になった三つの資源を指し示します。
- **第2部: 変わらないもの** — アペタイトとシェイピングがなぜ破棄されず、むしろ重くなるのか、その代わりに中身がどう再定義されるのかを扱います。
- **第3部: 新しいサイクル** — 6週間サイクルと2週間の[クールダウン](https://basecamp.com/shapeup/2.2-chapter-08)(cool-down)がどんなリズムへ圧縮されるのか、ベットと完了判定がどう書き直されるのかを見ていきます。

Shape Upを読んでいなくても本ガイドは追えます。原作の概念が初めて出てくるたびに短い説明を添え、[無料で公開されている英語原書](https://basecamp.com/shapeup)の該当章へリンクを張ってあります。原作をすでにご存じの方は、各章で「原作のどの仕掛けが、どの方向へ裏返るのか」だけを追って読んでも構いません。

## 本ガイドが扱わないもの

特定のAIツールの使い方は扱いません。どのエージェントをどんな設定で動かすかは半年もあれば変わりますし、その層の知識は本ガイドが語ろうとしているものとは寿命が違います。ツールは事例としてのみ登場します。

原作を置き換えようとする本でもありません。本ガイドはShape Upを読むための新しいレンズに近いものです。ここで「変わる」と述べている箇所も、原作を読んでいればずっと鮮明になります。

最後に、実務プロセスの完全な定義は本ガイドの役目ではありません。その席はロボコの[VDLC(Vibe-Driven Development Lifecycle)](https://vdlc.roboco.io)が担っています。本ガイドは、原作からVDLCへ渡るための橋です。なぜサイクルが短くなるのか、なぜ検証が独立した段階へ格上げされるのかを説明したうえで、では実際にどう運用するのかはVDLCの定義に引き渡します。橋の上で目的地を建て直すことはしません。
